# Local patches (not upstream)

This working tree runs the `pi-herdr-agents` extension **directly** (`pi install /Users/zhongyuan/Documents/github/pi-herdr-agents`; the published npm copy was removed). Everything below is a **local modification** kept on branch `local/task-route` so upstream can be pulled at any time with a small conflict surface.

`main` stays byte-identical to `origin/main`. The branch is pushed only to the personal mirror `vinsli/pi-herdr-agents` (remote `fork`, `git push fork local/task-route`) as backup; it is never pushed to upstream, never version-bumped, never released.

## 1. What this fork does

The `subagent` tool's `model` parameter accepts exactly one shape: `task:<category>`, where `<category>` is one of `coding`, `review`, `recon`, `qa`, `architecture`, `docs`.

- Concrete models come **only** from the authenticated candidates of `models.tasks[<category>]`, in configured order.
- A missing, empty, direct (`provider/model-id`), fallback-list (`a/x,b/y`), or unknown-category value is refused **before** any Herdr pane, worktree, or child process exists.
- `models.agents` and `models.default` are still parsed but are **no longer consulted** by the launch path.
- A role definition that sets `model:` is **refused** rather than silently ignored (see §3).
- Worktree launches use the first authenticated candidate only. Persistent specialists never advance past the first candidate.
- An ordinary, non-persistent launch appends the **parent runtime** as its last candidate, so an exhausted shortlist degrades instead of failing. That candidate is skipped when the parent model is outside the session's model scope.
- `/worktree` handoff and `subagent_resume` are the two exceptions: they inherit the parent runtime and do not pass through this admission.

## 2. Why

The intent is that every delegation is routed by task category through the durable task-model preferences, instead of callers hand-picking model IDs — and that a failing model degrades along an ordered candidate list rather than aborting the run.

## 4. Deviations from `docs/task-routed-subagents-plan.md`

The spec is upstream text and stays untouched; these deviations live here instead.

1. The spec names `pi-extension/subagents/index.ts` as the schema owner. The public `subagent` schema actually lives in `pi-extension/subagents/catalog.ts`.
2. The spec's Stage 1 assumes the working tree is what runs. True here now: the npm copy is removed and the package is registered as a local path.
3. The spec does not mention that a required `model` is a breaking schema change gated by `test/maestro/tool-schema.test.ts` against `test/fixtures/tool-schema/released.json`. Locally that gate stays red by design (§6).
4. The spec does not name the two implicit parent-inheritance paths: the `/worktree` handoff and `operations.prepare` in `maestro/runtime/pi-run-session.ts` (used only when `kernel.spawn` receives no prepared plans; the production tool path always supplies them).
5. The spec's acceptance criterion 8 (the ledger records the category) needed no change to `maestro/core/accept.ts`: the strict resolver keeps `requestedModel` equal to the raw `task:<category>` string.
6. **Not in the spec: the parent-runtime fallback.** An ordinary launch's candidate list ends with the parent runtime (skipped when the parent is out of scope). Without it, an exhausted shortlist would fail a run the parent could have completed.
7. **Not in the spec: role `model:` is refused.** The spec is silent; silently ignoring it would break role packs without a trace, so the launch fails with an explicit message naming `task:<category>`.
8. **Not in the spec: upstream tests are migrated, not skipped.** 52 upstream cases relied on direct IDs, fallback lists, or "omitted model inherits the parent"; they now select a task category, with the `recon` shortlist deliberately equal to the parent model to preserve the old intent. `test/maestro/tool-schema.test.ts` is the only expected red.

## 5. Durable configuration this fork requires

`$PI_CODING_AGENT_DIR/herdr-agents/config.json` must define all six categories with authenticated candidates, e.g.

```json
{
  "models": {
    "tasks": {
      "coding": ["provider/model-a", "provider/model-b"],
      "review": ["other-provider/model-c"],
      "recon": ["provider/model-a"],
      "qa": ["provider/model-a"],
      "architecture": ["other-provider/model-c"],
      "docs": ["provider/model-d"]
    }
  }
}
```

A category with no authenticated candidate is refused, so a missing entry makes that category unusable rather than falling back to a role or global default.

## 6. Expected red gates

- `test/maestro/tool-schema.test.ts` — "has no breaking change against the last released schema". `released.json` records the last published release and is never edited locally; a required `model` is by definition breaking. This one test stays red forever on this branch.
- `test/test.ts` — "public tool schema snapshot" also stays red on this branch (and currently on unmodified `origin/main` on this machine as well); it pins the generated schema snapshot that the breaking `model` change intentionally moves.
- Pre-existing on this machine, unrelated to the patch: several `test/launch.test.ts`, `test/worktree-cleanup.test.ts`, `test/verify-lab-guards.test.ts`, and `test/maestro/sidebar-fixture-ownership.test.ts` cases fail because macOS `/var` is `/private/var` (path equality) and Node 24 `rmSync` refuses a symlinked directory. They fail on unmodified `origin/main` too.

Everything else must be green: `npm run typecheck`, `npm run lint`, `npm run format:check`, `npm run docs:tools:check`, `git diff --check`.

## 7. Pulling upstream

```bash
git fetch origin
git switch local/task-route
git rebase origin/main
```

Conflict handling:

- `docs/tools.md` / `test/fixtures/tool-schema/current.json` — **never hand-merge**; take upstream's side, then re-run `npm run docs:tools` and continue:

  ```bash
  npm run docs:tools
  git add docs/tools.md test/fixtures/tool-schema/current.json
  git rebase --continue
  ```

- `pi-extension/subagents/catalog.ts`, `maestro/core/routing.ts` — small, sentence-level edits. If upstream rewrote the surrounding guidance, re-apply the local sentences from §3 by hand; the tests name the exact required strings.
  - Since upstream `c664e5e`, the four review-policy clauses ("For ordinary review…", same-family fallback, "context-isolated", "Cross-family verification…") live **only** in the `subagent` model description (`pi-extension/subagents/catalog.ts`) and in `maestro/core/config/task-model-init.ts`; catalogs and routing guidelines must not repeat them — both `test.ts` (exactly-once assertions) and `runtime-routing.test.ts` enforce it. Keep the fork's own sentences (the `task:<category>` admission lines, including the generic-branch line that must start with `For orchestrated subagent work`) and drop any duplicated review clauses when resolving conflicts.
- `test/test.ts`, `test/isolated-agent-dir.ts` — the fixture is the load-bearing part (`status` + `models.tasks`); re-apply it to upstream's helper if it moved.

Verify after every rebase:

```bash
npm test                 # only the released-schema check (plus the machine-only failures above)
npm run typecheck && npm run lint && npm run format:check && npm run docs:tools:check
```
